# 0004 — Keep the Excalidraw route, second

- **Status**: accepted
- **Date**: 2026-08-28

## Context

Excalidraw was not asked for: it appeared in a proposal at the end of a message,
and was then built. Three facts came out of building it, and they have to be
recorded because they nearly caused the route to be abandoned.

**An Excalidraw library cannot contain images.** Verified in
`@excalidraw/excalidraw` 0.18.1: `ExportedLibraryData` declares only
`{ type, version, source, libraryItems }`, with no `files` property, and
`loadLibraryFromBlob` returns nothing but `LibraryItem[]`. The deliverable could
therefore not be a stencil. We had to move to a **scene**, whose
`ExportedDataState` type does carry `files`.

**The free tier gives one persistent scene** in Excalidraw's cloud. Excalidraw+
(≈ $6–7/month/person) unlocks unlimited scenes, folders, access rights and
comments.

**draw.io has no real-time collaboration at all.** Its repository says so
explicitly: concurrent editing depends entirely on the storage backend. Its model
is asynchronous.

## Decision

**Keep the Excalidraw route, as the secondary one.** draw.io remains the
reference integration, cited first everywhere in the documentation.

## Justification

**The scene is the only artefact proving that the badges live outside
draw.io.** That is the decisive argument, and it is not one of usage but of
architecture: without a second consumer, nothing guarantees that the set has not
silently moulded itself to the constraints of a single tool. Tool independence
becomes verified by construction rather than hoped for.

**The free-tier limit does not bite on the intended usage.** It applies only to
scenes stored in Excalidraw's cloud. The format being plain JSON, the
`.excalidraw` files live in the git repository: you open them in the free editor
or in the VS Code extension, collaborate through a session link, and commit. The
cloud is never touched.

**On the collaboration axis it is Excalidraw that brings something**, not the
other way round: unlimited real-time collaborators on the free tier, where
draw.io does not offer the feature at all.

**The maintenance cost is close to zero**: one directory, one script, no
production dependency, regenerated by the same `regenerate.sh`.

## Consequences

### The accepted risk: silent rot

A route with no daily user breaks without anyone noticing. The risk is
**mitigated, not eliminated**: `scripts/excalidraw.mjs` carries a set of
conformance assertions that stop the build if the scene ceases to be valid —
missing base fields, a duplicate identifier, an image referencing a `fileId`
absent from `files`, a `dataURL` that does not decode back to SVG, a file not
named by its digest, a group that is not an image + text pair.

Those assertions verify **internal coherence**, not future compatibility with the
format. If Excalidraw changes its schema, they will keep passing. The version the
format was read against is recorded in the script and in `excalidraw/README.md`:
**0.18.1**.

### Other consequences

- The documentation cites draw.io first and Excalidraw as the alternative.
- Paying for Excalidraw+ is not justified as long as the files live in git. If
  usage shifts to a shared team space, this ADR has to be reopened — and the
  comparison will have to include the fact that draw.io's team tier (Confluence
  and Jira plugins) is paid too.

## Alternatives ruled out

- **Betting everything on draw.io.** Rejected: it loses the guarantee of tool
  independence, which is the only real contribution of this route.
- **Publishing a `.excalidrawlib` library.** Impossible: the format does not
  carry images. A library would display nothing but empty frames.
- **Shipping nothing and relying on SVG drag and drop.** Excalidraw does indeed
  accept an `.svg` dropped onto the canvas, and it works with nothing installed —
  that is documented in `excalidraw/README.md`. But it provides neither the label
  composed by the tool, nor the verification that the set survives a second
  consumer.
